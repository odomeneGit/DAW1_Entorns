01
FILOSOFIA I METODOLOGIA

Desenvolupament guiat per proves (TDD)

La qualitat d'una aplicació no depèn únicament que el programa s'executi. També cal comprovar que cada part fa allò que s'espera i que els canvis posteriors no trenquen funcionalitats que ja funcionaven.

Test-Driven Development (TDD)

És una manera de desenvolupar en què primer es defineixen proves que descriuen el comportament esperat i després s'escriu el codi necessari perquè aquestes proves se superin. És una pràctica associada a Extreme Programming (XP).

Per què necessitem proves unitàries?

Tradicionalment, sovint es deixaven les proves per al final i es comprovava l'aplicació sencera manualment. Aquesta manera de treballar pot fer que els errors es detectin tard i que, després d'una modificació, calgui repetir moltes comprovacions manuals.

Prova unitària

Comprova una unitat petita del programa, habitualment un mètode o una classe, amb unes dades concretes i un resultat esperat.

Prova de regressió

Es torna a executar un conjunt de proves després d'un canvi per comprovar que les funcionalitats anteriors continuen funcionant.

El cicle TDD

01TestDefinir el comportament
→
02RedLa prova falla
→
03GreenFer-la passar
→
04RefactorMillorar el codi
  1. Es crea una prova unitària que descriu el resultat correcte esperat.
  2. S'executen les proves: la nova ha de fallar perquè encara no s'ha implementat la funcionalitat.
  3. S'escriu el codi mínim necessari perquè la prova passi.
  4. Es tornen a executar totes les proves per comprovar el progrés i evitar regressions.
  5. Es refactoritza el codi, és a dir, se'n millora l'estructura sense canviar-ne el comportament. Es repeteix el cicle.
Objectes simulats (mock objects)Quan una part del sistema depèn d'una altra que encara no està disponible o que no volem executar durant la prova, podem utilitzar objectes simulats per representar aquesta dependència.

Avantatges i límits

  • Els errors es detecten abans i en una part concreta del codi.
  • Les proves es poden executar moltes vegades, de manera automàtica.
  • Faciliten les proves de regressió i els canvis amb més confiança.
  • Poden integrar-se en eines de construcció i integració contínua, com Maven.
  • Obliguen a pensar quin comportament ha de tenir el programa abans d'implementar-lo.
Atenció: passar les proves no demostra que el programa sigui perfecte

Només indica que el codi s'ha comportat correctament davant dels casos que hem dissenyat. Si no hem previst una situació, les proves poden no detectar-ne l'error.

02
FRAMEWORK DE PROVES

JUnit: què és i com funciona?

JUnit és una llibreria i un framework de Java per crear i executar proves unitàries. Va ser creat per Kent Beck i Erich Gamma i forma part de la família de projectes xUnit.

Una prova executa el mètode que volem comprovar amb unes dades d'entrada i compara el resultat obtingut amb el resultat esperat. Si coincideixen, la prova passa; si no, JUnit informa d'una fallada. També pot detectar excepcions inesperades.

Test case

És un cas de prova concret. En JUnit 5, habitualment es representa amb una classe que conté mètodes anotats amb @Test.

Test suite

És un conjunt de casos o classes de prova que es poden executar agrupats.

Què comprova una prova?

Exemple conceptualEntrada → sortida
Entrada:  2 i 3
Operació: sumar(2, 3)
Esperat:  5
Obtingut: 5
Resultat: PASSAT
Versió utilitzada en aquesta teoria

Tots els exemples d’aquesta pàgina utilitzen JUnit 5 (JUnit Jupiter). Farem servir les anotacions i les eines actuals d’aquesta versió, sense barrejar-les amb altres models de proves.

Afegir JUnit al projecte

Eclipse ofereix assistents per crear proves i configurar la llibreria. En projectes Maven, és preferible declarar la dependència al fitxer pom.xml, perquè Maven la descarrega i la gestiona automàticament.

pom.xml · JUnit 5Dependència de test
<dependencies>
  <dependency>
    <groupId>org.junit.jupiter</groupId>
    <artifactId>junit-jupiter</artifactId>
    <version>5.11.4</version>
    <scope>test</scope>
  </dependency>
</dependencies>

<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-surefire-plugin</artifactId>
      <version>3.5.2</version>
    </plugin>
  </plugins>
</build>

Després de desar el fitxer, a Eclipse podem fer clic dret sobre el projecte i seleccionar Maven → Update Project. Maven descarregarà les dependències necessàries. En un projecte Java que no utilitza Maven, l'assistent de creació de proves de l'IDE pot afegir la biblioteca JUnit al build path.

Preparar i validar les proves

Assertions: comprovar el resultat

Les assertions són mètodes que comparen el resultat real amb la condició esperada. Si la condició no es compleix, el test falla.

AssertionQuè comprova?Exemple
assertEquals(esperat, actual)Que dos valors siguin iguals.assertEquals(5, suma(2, 3))
assertNotEquals(a, b)Que dos valors siguin diferents.assertNotEquals(0, resultat)
assertTrue(condicio)Que una condició sigui certa.assertTrue(edat >= 18)
assertFalse(condicio)Que una condició sigui falsa.assertFalse(llista.isEmpty())
assertNull(obj)Que l'objecte sigui null.assertNull(resultat)
assertNotNull(obj)Que l'objecte no sigui null.assertNotNull(compte)
assertSame(a, b)Que dues referències apuntin al mateix objecte.assertSame(a, b)
assertNotSame(a, b)Que siguin objectes diferents.assertNotSame(a, b)
assertArrayEquals(a, b)Que dos arrays tinguin els mateixos elements i ordre.assertArrayEquals(a, b)
assertThrows(Tipus.class, executable)Que s'hagi produït una excepció concreta.assertThrows(IllegalArgumentException.class, ...)
assertDoesNotThrow(executable)Que l'execució no llanci cap excepció.assertDoesNotThrow(() -> servei.obtenir())
fail("missatge")Força que el test falli.fail("No hauria d'arribar aquí")

Per comparar nombres decimals amb precisió limitada, es pot indicar una tolerància (delta):

Comparació de decimalsJUnit 5
assertEquals(0.5, resultat, 0.000001);

Comprovar excepcions i temps

assertThrows i @TimeoutJUnit 5
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.Timeout;
import java.util.concurrent.TimeUnit;

@Test
void dividirPerZero() {
    assertThrows(ArithmeticException.class,
        () -> Calculadora.dividir(10, 0));
}

@Test
@Timeout(value = 100, unit = TimeUnit.MILLISECONDS)
void haDeSerRapid() {
    Calculadora.sumar(2, 3);
}
Independència de les provesUn test no hauria de dependre de l'ordre d'execució ni dels resultats d'un altre test. Cada prova ha de preparar les seves pròpies dades i deixar el sistema en un estat controlat.

ECLIPSE 2025-06 · 4.36.0

Crear i executar una prova a Eclipse

Partim d'un projecte Java que conté la classe que volem provar. A continuació crearem una classe de test separada i l'executarem des d'Eclipse.

  1. Selecciona la classe que vols provar dins de Package Explorer.
  2. Obre File → New → JUnit Test Case. També pots fer clic dret al paquet i seleccionar New → JUnit Test Case.
  3. Indica el nom de la classe de prova, normalment el nom de la classe original acabat en Test (per exemple, CalculadoraTest).
  4. Selecciona la versió de JUnit adequada (JUnit 5/Jupiter per als exemples actuals) i prem Next o Finish.
  5. Si Eclipse indica que cal afegir la biblioteca JUnit, accepta-ho si el projecte no la té configurada. En projectes Maven, comprova que la dependència existeix al pom.xml.
  6. Afegeix els mètodes anotats amb @Test i les assertions corresponents.
  7. Desa el fitxer i comprova que no hi hagi errors de compilació a la vista Problems.
  8. Fes clic dret sobre la classe de test i selecciona Run As → JUnit Test.
Important: Errors i fallades no són el mateix

Un error de compilació (per exemple, un import incorrecte) impedeix executar el test. Una fallada (failure) vol dir que el test sí que s'ha executat, però una assertion no s'ha complert. Un error d'execució (error) acostuma a indicar una excepció inesperada.

CODI I CASOS PRÀCTICS

Exemples de proves unitàries

Exemple 1. Classe i test en fitxers separats

La classe MyNumber representa un nombre enter i ofereix operacions de suma i resta. La classe de prova comprova que els resultats siguin els esperats.

MyNumber.javaClasse que provem
package com.test;

public class MyNumber {
    private int number;

    public MyNumber(int number) {
        this.number = number;
    }

    public int getNumber() {
        return number;
    }

    public MyNumber add(MyNumber another) {
        return new MyNumber(this.number + another.number);
    }

    public MyNumber sub(MyNumber another) {
        return new MyNumber(this.number - another.number);
    }
}
MyNumberTest.javaJUnit 5
package com.test;

import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

class MyNumberTest {
    private MyNumber number1;
    private MyNumber number2;

    @BeforeEach
    void setUp() {
        number1 = new MyNumber(2);
        number2 = new MyNumber(1);
    }

    @Test
    void sumaCorrectament() {
        assertEquals(3, number1.add(number2).getNumber());
    }

    @Test
    void restaCorrectament() {
        assertEquals(1, number1.sub(number2).getNumber());
    }
}

Exemple 2. Calculadora i un error amb els decimals

La calculadora següent treballa amb nombres enters. Això és important: en Java, si dividim dos enters, el resultat també és enter i es descarta la part decimal.

Calculadora.javaClasse que provem
public class Calculadora {
    public static int sumar(int a, int b) { return a + b; }
    public static int restar(int a, int b) { return a - b; }
    public static int multiplicar(int a, int b) { return a * b; }
    public static int dividir(int a, int b) { return a / b; }
}
CalculadoraTest.javaJUnit 5
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.Test;

class CalculadoraTest {
    @Test
    void operacionsBasiques() {
        assertEquals(3, Calculadora.sumar(1, 2));
        assertEquals(1, Calculadora.restar(2, 1));
        assertEquals(6, Calculadora.multiplicar(2, 3));
    }

    @Test
    void divisioEntera() {
        assertEquals(0, Calculadora.dividir(1, 2));
    }

    @Test
    void dividirPerZeroLlançaExcepcio() {
        assertThrows(ArithmeticException.class,
            () -> Calculadora.dividir(1, 0));
    }
}
Per què no podem esperar 0,5?

En el codi 1 / 2, els dos operands són enters. Per tant, Java calcula una divisió entera i retorna 0. Si volem un resultat decimal, hem de canviar el tipus de retorn i convertir almenys un operand a double.

Versió amb divisió decimalRetorn double
public static double dividir(double a, double b) {
    return a / b;
}

// A la classe de test:
assertEquals(0.5, Calculadora.dividir(1, 2), 0.000001);

Exemple 3. Pila: setUp(), tearDown() i independència

Una pila és una estructura LIFO (Last In, First Out): l'últim element que entra és el primer que surt. En aquest exemple, posar() afegeix elements, treure() n'extreu el darrer i tamany() retorna quants elements hi ha.

Pila.javaImplementació
import java.util.ArrayList;
import java.util.List;

public class Pila {
    private final List<Object> llista = new ArrayList<>();

    public int posar(Object objecte) {
        llista.add(objecte);
        return tamany();
    }

    public int tamany() {
        return llista.size();
    }

    public Object treure() {
        if (llista.isEmpty()) return null;
        return llista.remove(llista.size() - 1);
    }
}
PilaTest.javaJUnit 5
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

class PilaTest {
    private Pila pila;

    @BeforeEach
    void setUp() {
        pila = new Pila();
        pila.posar("Marisol");
        pila.posar("Santiago");
        pila.posar("Diego");
        pila.posar(23);
    }

    @Test
    void comprovaMida() {
        assertEquals(4, pila.tamany());
    }

    @Test
    void desapilaEnOrdreLifo() {
        assertEquals(23, pila.treure());
        assertEquals("Diego", pila.treure());
        assertEquals("Santiago", pila.treure());
        assertEquals("Marisol", pila.treure());
        assertEquals(0, pila.tamany());
    }

    @Test
    void treureDePilaBuidaRetornaNull() {
        while (pila.treure() != null) { }
        assertNull(pila.treure());
    }
}

@BeforeEach crea una pila nova i hi afegeix les dades abans de cada test. Així, comprovaMida() no depèn del que hagi fet desapilaEnOrdreLifo(). Cada prova comença en un estat conegut.

Exemple 4. Compte bancari

Podem provar diferents situacions d'un compte: consultar saldo, ingressar diners i retirar-los amb una contrasenya correcta o incorrecta i amb saldo suficient o insuficient.

Compte.javaClasse que provem
public class Compte {
    private int saldo;
    private String contrasenya;

    public Compte(int saldoInicial, String contrasenya) {
        this.saldo = saldoInicial;
        this.contrasenya = contrasenya;
    }

    public int diposita(int quantitat) {
        saldo += quantitat;
        return saldo;
    }

    public int retira(int quantitat, String clau) {
        if (!contrasenya.equals(clau)) return -2;
        if (saldo < quantitat) return -1;
        saldo -= quantitat;
        return quantitat;
    }

    public int getSaldo() { return saldo; }
}
CompteTest.javaJUnit 5
import static org.junit.jupiter.api.Assertions.*;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

class CompteTest {
    private Compte compte;

    @BeforeEach
    void setUp() {
        compte = new Compte(5000, "joan77");
    }

    @Test
    void saldoInicial() {
        assertEquals(5000, compte.getSaldo());
    }

    @Test
    void ingressaDiners() {
        assertEquals(5560, compte.diposita(560));
    }

    @Test
    void contrasenyaIncorrecta() {
        assertEquals(-2, compte.retira(200, "pere"));
    }

    @Test
    void saldoInsuficient() {
        assertEquals(-1, compte.retira(20000, "joan77"));
    }

    @Test
    void retiradaCorrecta() {
        assertEquals(250, compte.retira(250, "joan77"));
        assertEquals(4750, compte.getSaldo());
    }
}
Què estem comprovant?Els casos cobreixen el saldo inicial, un ingrés, una contrasenya incorrecta, un saldo insuficient i una retirada vàlida. En una aplicació real també provaríem quantitats negatives, valors nuls i altres regles del negoci.

AGRUPAR I AUTOMATITZAR

Test suites i proves de regressió

Quan el projecte creix, és habitual tenir diverses classes de prova. Una suite permet agrupar-les i executar-les com un conjunt.

Com s’agrupen les proves?

En els projectes Maven amb JUnit 5 no cal crear manualment una classe suite per executar totes les proves habituals. Maven, mitjançant el connector Surefire, localitza i executa les classes de test que segueixen les convencions de noms i configuració del projecte. També podem executar una classe concreta des d’Eclipse.

JUnit 5 i Maven

Amb JUnit 5, podem executar totes les proves del projecte amb l'opció Run As → Maven test o des d'un terminal amb:

TerminalMaven
mvn test

Maven executa les proves detectades pel seu proveïdor de tests i mostra el resum. En una pipeline d'integració contínua, aquesta ordre pot formar part del procés de construcció: si una prova falla, la construcció pot marcar-se com a fallida.

Failures

La prova s'ha executat, però una assertion no ha trobat el resultat esperat.

Errors

Durant la prova s'ha produït una excepció inesperada o un problema que ha impedit completar-la correctament.

Proves independents

JUnit crea el context d'execució de cada test d'acord amb el seu model. No hem de confiar que un test anterior hagi deixat preparades les dades d'un altre. Fem servir @BeforeEach per inicialitzar l'estat que necessitem.

PROVES EN APLICACIONS WEB

JUnit i les aplicacions web

En una aplicació web Java podem utilitzar JUnit per provar les classes i la lògica de negoci, com ara serveis, validacions, càlculs o accés a dades (si les dependències estan controlades).

Quan volem provar la navegació web, els formularis, les respostes HTTP i la interacció amb les pàgines, necessitem eines de proves d'integració o d'extrem a extrem. El material original esmenta JWebUnit, una eina orientada a provar aplicacions web. És una tecnologia antiga i convé comprovar-ne la compatibilitat abans d'utilitzar-la en projectes actuals.

JUnit

Prova unitats de codi Java: mètodes, classes i lògica de negoci.

Proves web

Comproven el comportament de la web: formularis, navegació, peticions, respostes i fluxos complets.
